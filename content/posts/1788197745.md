Managing `.env` variables without a secret management mechanism specially for devs working on 10’s of different things and multiple repos. Once committed into any remote git forge it becomes a hurdle to remember which `.env`  is of which project even after using password manager just a week later. So here comes the role of secrets management and the better way is to manage secrets in my view / the easiest way to let them live with your code. Thanks to time tested algorithms like AES256 and pgp which are not so easy to crack . Read what nist has to [say about this.](https://csrc.nist.gov/csrc/media/Events/2024/fifth-pqc-standardization-conference/documents/papers/on-practical-cost-of-grover.pdf)  Tbh there is no one using something like pgp/gpg for encryption it’s more or less a paper tiger because of it’s hardness and no one barely knows how to use pgp. And to make pgp work you need the recipient to be able to decrypt the message. I doubt 99% of the people can’t even decrypt their own file after a week. So using pgp is a big no. It’s similar to loosing `.env` . There comes age as an encryption it’s modern, robust easy to use and manageable asymmetric keys also age can be used with ssh, Pgp type keys for encryption.  

Also there comes [age encryption](https://github.com/filosottile/age) which is a modern easy to use asymmetric encryption.  will later discuss on how to use age later on.

### I am assuming that you are using some sort of \*nix based operating system if not then use WSL(windows subsystem for Linux) to follow along.

Here we will be using something like [sops](https://github.com/getsops/sops) .Sops is a cncf sandbox project so it’s matured enough for testing.

But writing yaml files for anything should not be a job of humans additionally no one can write a single file in one go without a proper Ide with linter

Why doing the hard way when, it should and can be done in a simple easy way. 

So introducing [mise](https://mise.jdx.dev/)  my favourite tool nowadays to manage dev env , tasks, handling environment variables, Generally it’s not recommended to pin “latest“ but i am a drinker of mountain dew “(daar ke age jeet hai)” something similar to that 😏. 

> 💡 To generate a mise.toml run \`mise gen config\` and choose tools you need from the tui (terminal user interface)



```yaml
[tools]
age = "latest"
sops = "latest"

[env]
SOPS_AGE_RECIPIENTS = "{your age recipients here}, {yet another recipient}"
_ = { file = "{ path = .env }" }

[tasks]
encrypt = "sops -e -i .env && mv .env .env.example"
decrypt = "mv .env.example .env && sops -d -i .env"
```

This is generally my overall workflow regarding secrets. BTW, the public key is shareable as it’s name, public, 

export an env variable system wide 

```bash
export SOPS_AGE_KEYS="AGE_PRIVATE_KEY_HERE" 
```

or, you can use 

```sh
export SOPS_AGE_KEY_FILE="$HOME/.sops/age/keys.txt"
or 
export SOPS_AGE_KEY_FILE="$HOME/.config/sops/age/keys.txt"
```

keep the contents of keys.txt safe in some password manager only .  

AGE supports YubiKey, ssh-agent as a helper too.
