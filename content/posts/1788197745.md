Managing `.env` Variables without a secret management workflow gets messy, especially if you work across many projects and repositories. Once values are scattered or committed by mistake, it becomes hard to remember which `.env` Belongs to which project, even with a password manager.

I prefer keeping encrypted secrets close to the code. Algorithms like AES-256 and PGP are strong in theory (see [NIST's discussion](https://csrc.nist.gov/csrc/media/Events/2024/fifth-pqc-standardization-conference/documents/papers/on-practical-cost-of-grover.pdf)), but PGP is difficult for most people to use correctly in day-to-day workflows. If you cannot reliably decrypt your own files later, the setup is not practical.

Age is a simpler alternative. It uses modern cryptography, has manageable keys, and can work with existing credentials such as SSH keys. In this post, I use age with SOPS to encrypt secrets while keeping them in the repository.

### I am assuming that you are using some sort of \*nix based operating system if not then at least use WSL(windows subsystem for Linux) to follow along.

In this guide, we will use Sops (Secret Operations) to manage and encrypt our secrets. Sops is a CNCF sandbox project; it originated as a Mozilla initiative before being donated to the open‑source community.

Sops can manage Yaml, Toml, dotenv, env.json.

![](https://s6.imgcdn.dev/Y8IpEH.png)



But writing yaml files for configuration is something no one should be doing.

Why doing GitOPS the hard way, also by not committing environment variables you are not creating a reference so that others can collaborate on the project, SOPs is very selective at encryption it just encrypts the values not the keys. 

Introducing [**mise**](https://mise.jdx.dev/) my go to tool for managing development utilities, automating tasks, and handling environment variables. While best practice advises against pinning to “latest,” I’ve chosen to do so for now.

> 💡 To generate a mise.toml run \`mise gen config\` and choose tools you need from the Tui (terminal user interface)



```yaml
[tools]
age = "latest"
sops = "latest"

[env]
SOPS_AGE_RECIPIENTS = "{your age recipients here}, {yet another recipient}"
_ = { file = "{ path = .env }" }

[tasks]
encrypt = "sops -e -i .env && mv .env .env.example"
decrypt = "mv .env.example .env && sops -d -i .env"
```

This is generally my overall workflow for secrets. The public key is safe to share.

Export an `.env` Variable system wide generally from the dot `rc` File like .bashrc, .zshrc etc

```bash
export SOPS_AGE_KEYS="AGE_PRIVATE_KEY_HERE" 
```

or, you can use 

```sh
export SOPS_AGE_KEY_FILE="$HOME/.sops/age/keys.txt"
or 
export SOPS_AGE_KEY_FILE="$HOME/.config/sops/age/keys.txt"
```

Keep the contents of keys.txt safe in some password manager only .  

AGE supports YubiKey, ssh-agent as a helpers too.
